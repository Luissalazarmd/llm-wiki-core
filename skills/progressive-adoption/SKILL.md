# Progressive adoption

Help the person start from an existing wiki, collected material or a first question. Identify their starting point, then adapt a small part in place rather than requiring a replacement library. This is the same Bibliotecario's procedure, with no migration runtime, new bot or automatic metadata conversion.

## When to Use

- The person wants to start using Core, with or without an existing library, or incorporate a previously untouched part.
- The current organization/schema makes a useful task difficult and a small reviewed correspondence would help.
- Do not run as a mandatory prerequisite for ordinary reading, as a whole-vault audit or as permission for bulk migration.

## Prerequisites

Identify whether a library exists before requiring its path or configuration. When it exists, locate it independently of the Core checkout. Establish a small authorized sample and current question, applicable trusted rules, privacy/provider-transmission scope and permitted tools before reading content. Default to read-only. A library's managed writer and stronger custody rules prevail; missing capabilities mean proposal-only for affected writes, not a replacement engine.

## Identify the starting point

Use the current conversation, explicitly supplied locations/files and authorized project context first. If the material and location are already known, acknowledge them and continue; do not ask the person to repeat information. Detection is bounded observation, not permission: do not search the device, home directory, accounts or private collections to discover a wiki. Missing accessible evidence means unknown is not absent.

When necessary, ask one short question about what the person has and where they are, in the person's language: “Do you already have a wiki or notes, collected articles to read, articles you have written, or are you starting from scratch? Where are they, or which one would you like to start with?” Ask only the missing part and clarify whether ambiguous “articles” means external reading or authored work. These starting points can coexist; do not force one exclusive category.

- **existing wiki:** follow its rules and select a small source/question plus related notes. Preserve working organization; use the sample procedure below.
- **collected articles:** start with one provided article and a question. A wiki is not a prerequisite for reading. Distinguish external sources from personal annotations; propose a minimal library location and required MOC/root/taxonomy only if retaining new captures is requested. No bulk import.
- **authored articles:** preserve authorship, published/draft status and existing location. Select a section, references or research question with permission; keep manuscripts in their authoring responsibility, not automatic Raw or accepted Wiki. Derive reusable notes only through their own review.
- **starting from scratch:** start with one question or supplied source. Offer a minimal private location outside the public Core checkout only when saving is wanted, with no automatic folder creation. Explain any missing capture classification and propose the smallest reviewed setup; do not ask the person to design the architecture. Do not fabricate an existing sample or claim bootstrap support in helpers that require existing parents.

After identifying the starting material and access scope, proceed with only applicable steps. No existing explanation means a new-note proposal may be appropriate; no available originals means source-dependent claims stay unverified. Creating initial directories/maps/settings needs explicit permission and permitted host tools; Core adds no initialization runtime. Ordinary reading or a conversation can continue while that setup remains deferred.

## Procedure

1. **Observe a sample.** Read rules first, then selected originals and representative related notes. Use the host's bounded file/search tools or scoped existing-mode discovery; do not scan the whole library. Inventory attachments by locator without decoding unless separately allowed. Report only the paths actually inspected and ambiguities. Do not infer source ownership, maturity or acceptance from filenames, folder names or a label.
2. **Distinguish what already exists.** Separate external sources and versions, personal notes/observations with preserved authorship, existing syntheses, maps and author drafts. A personal hypothesis is not independent evidence; an imported synthesis is not automatically accepted. Keep mixed folders mixed: propose per-file selections instead of marking every descendant as a source. Do not put everything in Raw or recast the user's prose as an external capture.
3. **Explain a minimal correspondence.** In the person's language, show which existing paths can fulfill Raw preservation, Review proposals and Wiki maintained-knowledge responsibilities, and which stay unresolved/private authoring. Explicitly state that mapping is not acceptance. Existing material stays at its current bytes and paths; do not move, copy, rename or rewrite originals or rules. Raw/Review/Wiki need not become physical folders. Ask for confirmation of the correspondence only where recording/applying it changes the workflow; do not make the person operate JSON or a metadata questionnaire.
4. **Prepare the first useful case.** Select one source and one related explanation or question. Search within the granted scope for the same source/version and already-developed ideas. Reuse instead of duplicating; distinguish an exact duplicate from added evidence, a changed source version or a genuinely different argument. Contrast claims against original locators and explain the contribution, tension or gap. Propose an update of the existing explanation when continuous; create a new derived note only when justified. New source capture follows [capture/classify](../capture-source/SKILL.md); existing originals need no retroactive admission rewrite. Missing MOC/root/taxonomy blocks a new capture, not reading. Creating missing maps/taxonomy requires a separate exact reviewed proposal, never arbitrary classification to pass a checker. Unsafe or unsupported schema stays unchanged; offer a compatible reviewed derived note only where library rules permit it.
5. **Present and adapt.** Show the full new content or exact update diff plus readable result, original/idea lineage, current/proposed maturity and limitations. Obtain actual confirmation of that version under [propose/review/retain](../review-save/SKILL.md). An adoption request or correspondence approval is not note approval, permission expansion or automatic acceptance. If repeated use benefits from settings, prepare one private config separately with authorization; record only reviewed path correspondence, default read-only, and exclude private settings from publication. Do not declare a mixed parent folder immutable when only an explicit source file is known. The actual permitted writer performs the confirmed change with version checks and recovery; no unattended migration.
6. **Verify and continue lightly.** Read back the exact changed target, preserve all other originals/authorship/links, verify unchanged bytes and paths and demonstrate scoped retrieval of the result and its relevant source. Report the sample handled, proposed versus confirmed versus saved, unresolved entries and next useful task. Reuse the existing authorized project note/continuity surface if one exists, not a second registry or backlog. Continue only on later requested cases or within an explicitly approved bounded scope; no whole-library completion claim.

## Pitfalls

Layer mapping expresses responsibility, not proof of quality, past review or current write permission. A new source's MOC hierarchy is organization, not idea maturity. Do not erase existing drafts, unsupported note formats, contradictions or duplicate candidates just to normalize the library. No automatic merging, deletion, moves, template enforcement, global uniqueness or universal host compatibility. Sensitive or licensed originals stay under their actual access/rights rules; local adoption does not authorize uploading their contents or changing providers. Plain helpers are cooperative tools, not a filesystem barrier.

## Verification

A first case is complete only when its approved adaptation is saved/read back through the permitted writer, the unchanged source/other selected files are accounted for, and the result is found again within scope. If no change is useful, demonstrate reuse with unchanged files; do not manufacture a note for a success count. If permission or a compatible writer is missing, report proposal-only or reading/reuse completed, not adoption saved. Tests of fixtures and skill wording establish tool/contract behavior, not real user decisions or automatic semantic classification. For acceptance, use a foreign organization without mandatory Raw/Wiki folders, preserve mixed-content authorship, and test denied/stale operations separately from a live human-guided pilot.
